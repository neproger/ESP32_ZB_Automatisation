# V2 → Rust: принцип портирования архитектуры Home Assistant

> Статус: **главный принцип проекта**.
> Источник проверенного поведения — `esp32-p4_HA_v2`.
> Рабочий план — [V2_TO_RUST_PORTING_PLAN.md](V2_TO_RUST_PORTING_PLAN.md).

## 1. Цель

Перенести существующую архитектуру и функциональность Home Assistant V2 на
Rust.

V2 уже реализован и проверен на реальном оборудовании. Нужно воспроизвести
эту реализацию на другом языке, а не проектировать новую систему.

```text
V2  — функциональный и архитектурный эталон
Rust — целевая реализация этого эталона
```

Результат должен сохранять поведение V2 и использовать уже подготовленные
Rust-компоненты, в частности `micro-db` и `ha-domain`.

## 2. Основной принцип

Работа выполняется последовательно, слой за слоем:

1. Изучить соответствующий слой V2.
2. Определить его назначение, ответственность, API и зависимости.
3. Изучить существующую Rust-инфраструктуру.
4. Реализовать эквивалентную функциональность на Rust.
5. Подключить слой к существующему Domain.
6. Проверить соответствие поведения исходной реализации V2.
7. Перейти к следующему слою.

Не нужно заранее реализовывать всю систему или проектировать дополнительные
механизмы.

Каждый слой переносится в контексте всей архитектуры, чтобы интерфейсы и
взаимодействие с остальными компонентами оставались согласованными.

## 3. Источник истины

При работе необходимо опираться на:

- фактическую реализацию Home Assistant V2;
- проверенное поведение V2 на оборудовании;
- существующие контракты и взаимодействия между слоями;
- уже реализованные Rust-компоненты;
- документацию V2 как описание архитектуры и назначения компонентов.

Если документация расходится с фактической реализацией V2, расхождение нужно
зафиксировать и проверить. Нельзя самостоятельно выбирать новую семантику или
менять поведение.

## 3.1. Допустимые отличия от V2

V2 является основным источником архитектуры, алгоритмов и поведения системы.
Однако портирование не означает обязательного буквального копирования каждой
реализации.

Предусмотрены два допустимых исключения.

### Исключение 1. Zigbee Layer

Zigbee-слой является особым случаем.

Его реализация не обязана полностью повторять Zigbee-механику V2, поскольку
при разработке текущего Zigbee-слоя использовались не только исходная логика
V2, но и отдельные архитектурные решения и механизмы Zigbee2MQTT (Z2M).

Поэтому:

- Zigbee-слой рассматривается как самостоятельная реализация;
- его архитектура может отличаться от Zigbee-слоя V2;
- допускается использование проверенных и полезных механизмов Z2M;
- не требуется искусственно приводить Zigbee-слой к реализации V2;
- Zigbee-слой обязан соблюдать общие контракты проекта и корректно
  взаимодействовать с Domain и остальными компонентами.

Zigbee — единственный заранее предусмотренный слой, для которого допускается
существенное архитектурное отличие от V2.

### Исключение 2. Уже реализованные улучшения

В ходе разработки Rust-версии могли появиться дополнительные решения,
улучшения и механизмы, которых не было в V2.

Не требуется автоматически удалять их ради полного совпадения с исходной
реализацией.

Каждое такое решение оценивается отдельно. Сохранять его можно, если оно:

- решает реальную техническую задачу;
- приносит практическую пользу;
- не дублирует существующую функциональность;
- не нарушает границы ответственности слоёв;
- не усложняет систему без достаточных оснований;
- не меняет проверенное поведение V2 без необходимости.

Если решение полезно и обосновано, его следует сохранить и документировать как
отличие Rust-реализации от V2.

Если практической пользы нет или оно создаёт лишнюю сложность, его не следует
сохранять только потому, что оно уже реализовано.

### Приоритет правил

1. Для всех обычных слоёв — архитектура, алгоритмы и поведение V2.
2. Для Zigbee — существующая целевая архитектура Zigbee, включающая полезные
   механизмы Z2M.
3. Для уже реализованных улучшений — индивидуальная оценка полезности и
   совместимости.

Главная цель остаётся неизменной: сохранить проверенную механику V2, допуская
только осознанные и обоснованные отличия.

## 4. Что требуется

### 4.1. Перенести существующую функциональность

- Сохранить назначение каждого слоя.
- Сохранить алгоритмы и правила обработки данных.
- Сохранить существующие API-контракты по смыслу.
- Сохранить последовательность взаимодействия компонентов.
- Сохранить поведение при штатных и предусмотренных V2 ошибках.
- Учитывать ограничения ESP32 и ESP-IDF.

### 4.2. Использовать существующую Rust-инфраструктуру

- `micro-db` — низкоуровневое хранилище.
- `ha-domain` — центральный владелец канонического состояния.
- Остальные Rust-компоненты — по их уже определённой ответственности.

Не создавать параллельные реализации уже существующих механизмов.

### 4.3. Переносить постепенно

Для каждого слоя должны быть понятны:

- исходный компонент V2;
- его ответственность;
- используемые структуры данных;
- входные и выходные интерфейсы;
- зависимости;
- соответствующий Rust-компонент;
- результаты проверки эквивалентности.

После завершения слоя он становится частью общей Rust-системы.

## 5. Что не требуется

Не нужно:

- заново проектировать архитектуру Home Assistant;
- придумывать новые алгоритмы вместо проверенных алгоритмов V2;
- менять поведение ради предполагаемого улучшения;
- создавать дополнительные уровни абстракции без необходимости;
- добавлять новые механизмы хранения;
- проектировать отдельную систему миграции данных V2 → V3;
- создавать новые протоколы восстановления состояния;
- добавлять маркеры миграции, матрицы восстановления и дополнительные
  state machine, если этого нет в исходной механике V2;
- вводить новые гарантии транзакционности и отказоустойчивости, которых не
  было в V2;
- переписывать уже готовые Rust-компоненты без доказанной необходимости;
- переносить бизнес-логику в `ha-app`, если она принадлежит конкретному слою.

## 6. Правила принятия решений

Если при портировании возникает техническая проблема:

1. Сначала определить, как она решена в V2.
2. Проверить, можно ли воспроизвести это решение на Rust.
3. Если требуется языковая адаптация, сохранить исходную семантику.
4. Если точный перенос невозможен, описать ограничение и предложить
   минимальное изменение.
5. Не менять архитектуру или поведение без обоснования.

Rust-реализация может отличаться внутренним устройством, но не должна без
необходимости отличаться внешним поведением.

## 7. Критерий завершения

Портирование считается успешным, когда:

- функциональность исходного слоя V2 реализована на Rust;
- слой подключён к общей архитектуре через предусмотренные интерфейсы;
- взаимодействие с Domain соответствует его контрактам;
- проверки подтверждают соответствие исходному поведению;
- отсутствуют параллельные и временные реализации, оставленные вместо
  перенесённой функциональности.

## 8. Итоговый принцип

**Не придумывать новую систему. Не улучшать архитектуру по собственной
инициативе. Не усложнять проверенную механику.**

Последовательно переносить существующую реализацию Home Assistant V2 на Rust,
подключать каждый слой к готовому Domain и сохранять проверенное поведение
системы.
