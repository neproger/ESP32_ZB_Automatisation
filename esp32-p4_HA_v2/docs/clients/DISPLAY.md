# Display

Слой: **Clients / Display**. Карта системы — `../ARCHITECTURE.md`.
Документ описывает контракт и поведение; конкретная реализация — в коде.
Формы записей экранов — `ha_model/include/ha_model/ha_groups.h`; железо панели
(дисплей, тач, распиновка) — `../hardware/JC4880P443C_I_W.md`.

## 1. Роль

Display — локальный LVGL-интерфейс устройства. Это **осознанное исключение** из общего
правила подписки на события: обновлять LVGL на каждое событие дорого. Вместо подписки
Display сам периодически опрашивает Domain read API (прямой polling) — это его быстрый
путь. Read path остаётся за Domain; наружу типы хранилища не выходят.

## 2. Экраны — это данные (группы)

Экраны Display описывает пользователь через Web (как правила Automation), а Display их
только читает: раскладка — данные, а не код. Две сущности Domain, регистрируются из
bootstrap как любые другие (`../RECORD_MODEL.md` §1.1):

```text
group       — экран/дашборд: числовой ключ id (как у automation), payload — title
group_item  — виджет на экране: ссылка на состояние + order + title
```

`title` у экрана и у элемента задаёт пользователь, независимо от имени устройства:
одно и то же состояние на разных экранах подписано по-разному. Версии и временных
меток в записях нет — они в meta хранилища (`../RECORD_MODEL.md` §4).

Это **не** Zigbee-группы (`0x0004`, `../services/ZIGBEE.md` §8): здесь «группа» —
раскладка экрана, а не адресация ZCL.

Виджет ссылается на **состояние**, а не на endpoint, и берёт его готовым ключом Domain —
`ha_zb_state_key_t` (`(device_uid, endpoint, cluster_id, attr_id)`, `ha_entities.h`).
Новый ref для состояния не вводится.

Ключ `group_item` — составной `(group_id, ha_zb_state_key_t)`: **одно состояние можно
показать на нескольких экранах/дашбордах** (many-to-many). Оба компонента числовые и
фиксированной ширины (`../RECORD_MODEL.md` §5); строк в ключах нет.

Display держит только opaque-версии для сравнения и не дублирует данные Domain.

## 3. Обновление: meta, а не payload

Дешёвый сигнал «изменилось ли» даёт `domain_entity_meta(type, key, *meta)` — opaque
`domain_entity_version_t` без чтения записи (`../domain/DOMAIN_API.md` §7). Версия живёт
в meta хранилища и растёт только при реальном изменении payload (`../RECORD_MODEL.md` §4).

```text
poll meta(GROUP, id)                  → состав/имя изменились → перечитать items
for each item:
    poll meta(STATE, item.state_key)  → version != last → get → обновить виджет
```

- состояние — одна сущность на атрибут, поэтому обновляется конкретный виджет, а не
  экран целиком;
- топология (`device`, `endpoint`) и сами `group`/`group_item` тоже версионированы:
  переименование устройства, смена состава кластеров и членства видны по мете;
- список виджетов экрана — `domain_entity_iter(GROUP_ITEM)` с фильтром по `group_id`
  (prefix-фильтра в Domain пока нет; 256 записей обходятся целиком);
- `NOT_FOUND` из меты — сущности больше нет: виджет/экран удаляется;
- после reboot/erase RAM-таблиц версия сбрасывается к начальной: сравнивать
  `version != last`, а не `>`, либо на старте делать полный рендер. Flash-таблицы
  версию переживают.

## 4. Проекция виджета

Что рисовать — вычисляемая проекция, а не хранимая сущность. Тип виджета выводится из
пары `(cluster_id, attr_id)` состояния: числа — `ha_zigbee.h`, семантика — таблица
проекции (`../services/ZIGBEE_CAPABILITIES.md` §4). Display не изобретает имена и не
заводит вторую систему идентификаторов.

## 5. Команды

Управление (on/off, уровень, цвет) уходит командой через Domain, как у любого
потребителя (`../domain/COMMANDS.md`); прямого обращения к Zigbee-сервису нет.

## 6. Реализация и превью

Компонент `display`: `src/ui_*` зависит только от LVGL, Domain API и форм `ha_model`;
цвета живут в одном месте — `src/ui_palette.[ch]` (роли `UI_COL_*` — доступ к активной
палитре, пресеты Retro/Warm/Dark). Тема выбирается в настройках (`settings.palette_id`),
применяется пересборкой экранов (`display_request_theme_reload`). Кириллические шрифты
(`fonts/`, сгенерированы `lv_font_conv`, LVGL 9 —
встроенные шрифты кириллицу не содержат). Порт под плату — отдельный компонент
`display_p4/` (ST7701 MIPI-DSI + GT911 + esp_lvgl_port); он поднимает панель/тач и
зовёт `display_start(&s_domain)` из `app_main`.

Экран — одна группа (`lv_obj_create(NULL)`): шапка с названием и ниже скроллируемый
список, где сразу все виджеты группы (switch / slider / значение). На P4 ресурсов
хватает рисовать весь список, в отличие от S3 (там был один виджет за раз).
Вертикальная прокрутка — у списка; переход между группами — `lv_screen_load_anim`
влево/вправо, старый экран удаляется автоматически; горизонтальные жесты — на экране.

Строка состояния — на `lv_layer_top()`: живёт независимо от текущего экрана, поэтому
остаётся видимой при переходах. Показывает время и город системного устройства и
погоду: иконку условия + температуру + влажность из `HA_ENTITY_WEATHER`
(`../services/SYSTEM.md` §3.1). Иконки — **иконочные шрифты**: UI-хром из FontAwesome
(`icons/icons.txt` → `ui_icons`, `UI_ICON_*`), погода из Weather Icons
(`icons/weather_icons.txt` → `wicons`, `WEATHER_ICON_*`, набор целиком — строка `*`);
генератор `icons/tools/gen.mjs`. Глиф красится стилем `text_color`, поэтому следует теме.
Экраны резервируют под строку `UI_STATUSBAR_H` сверху.

Внизу — навигационные точки-карусель (`ui_nav_dots.c`): по одной на группу, активная
подсвечена; тоже на `lv_layer_top()`, поэтому не двигаются при переходах.

В строке состояния — «бургер» (`ui_menu.c`) с выпадающим меню на `lv_layer_top()`:
«Настройки» и «Wi-Fi». «Настройки» — отдельный экран (`ui_settings.c`): подсветка и
таймаут скринсейвера, чтение/запись `HA_ENTITY_SETTINGS` (`../services/SETTINGS.md`).
Контролы берутся из общей базы `ui_widgets` (`ui_slider_create_styled`,
`ui_dropdown_create_styled`) — не собираются в экране вручную.
Wi-Fi открывает отдельный экран (`ui_wifi.c`): список
сетей из `HA_ENTITY_WIFI_SCAN`, статус из `HA_ENTITY_WIFI_STATUS`, кнопка «Сканировать» и
диалог пароля (`lv_keyboard` + `lv_textarea`). Скан — команда `HA_CMD_WIFI_SCAN`,
подключение — `HA_CMD_WIFI_CONNECT` (args: ssid + пароль); результат приходит состоянием,
как и всё остальное (форм — `ha_model/ha_wifi.h`).

Превью без железа — LVGL Live Preview: тот же `ui/` + фейковый Domain с мок-данными
(`preview/domain_fake.c`), панель 480×800.

## 7. Открытые вопросы

- **Живое переключение темы.** Сейчас выбор темы (`settings.palette_id`) применяется
  пересборкой дерева экранов (`display_request_theme_reload`). Позже можно обновлять
  стили на месте, без пересоздания объектов.
- **Порядок экранов.** Явный `order` у `group` или порядок обхода (ключ/индекс)?
- **Список виджетов экрана.** Обход всех `group_item` с фильтром или prefix-запрос в
  Domain под потребителя (`DOMAIN_API.md` §7).
- **Проекция `(cluster, attr) → widget`.** Где живёт таблица (в Display или общий
  словарь) — решается при реализации виджетов; серверного `ha_capabilities.h` больше нет.
