# Единая модель записей

> **Статус:** принятый контракт проекта `esp32-p4_HA_v2`. Карта системы — `ARCHITECTURE.md`.
> Это **не план реализации**: конкретные структуры, имена и лимиты уточняются в коде.
> Документ обязателен для всех сервисов и для Domain.

## 1. Роль

**Запись (record)** — каноническое представление сущности Entity Store: блок байт
фиксированного размера, один на тип сущности.

```text
ha_model        владеет формой
app bootstrap   владеет политикой: состав типов, capacity, backing, persist_key
Domain          владеет механизмом и не знает concrete record types
Services        владеют семантикой и используют общие определения
```

Распределение ответственности:

| Кто | Что знает о записи |
|---|---|
| **Domain** | только descriptor: `type`, `key_size`, `payload_size`, `capacity`, `backing`, `persist_key`, optional validator |
| **Сервис-владелец** | семантика полей, допустимые значения |
| **Остальные сервисы** | layout (читают те же поля) |
| **App bootstrap** | какие типы существуют и как они хранятся |
| **Web service** | проекцию record → DTO для браузера |

Определения layout живут в компоненте **`ha_model`**, который линкуют сервисы и
bootstrap, но **не** Domain. Компонент расположен рядом с приложением
(`esp32-p4_HA_v2/ha_model`), а не в `shared_components/`: у него один потребитель
(прецедент — `MSTORE_IMPL_JOURNAL.md:166`). Перенос — при втором потребителе.

### 1.1. Регистрация

Domain не содержит таблицы известных типов и не включает `ha_model`. Он получает
descriptor через единый механизм:

```c
domain_entity_desc_t desc = {
    .type         = HA_ENTITY_DEVICE,
    .key_size     = sizeof(ha_device_key_t),
    .payload_size = sizeof(ha_device_record_t),
    .capacity     = APP_DEVICE_CAPACITY,
    .backing      = DOMAIN_BACKING_RAM_FLASH,
    .persist_key  = "device",
};

domain_register_entity(domain, &desc);
```

Этот код принадлежит **bootstrap приложения**, а не сервису: `device` создаёт Zigbee, но
читают его Web, Automation и другие. Владение таблицей системное, а не владение одного
потребителя. API общий — без `domain_register_device()` и подобных имён: Domain не должен
знать этих слов.

Bootstrap остаётся единственным местом, где собраны реальные экземпляры таблиц и их
ёмкости — ровно то, что нужно для пересчёта размера раздела.

Числовой `entity_type` (`HA_ENTITY_DEVICE`, `HA_ENTITY_ENDPOINT`, …) — **внутренняя
runtime identity Domain**, а не wire ABI. Порядок значений внутри прошивки свободный.
Наружу (WS) тип передаётся строковым именем (`"device"`, `"endpoint"`, `"automation"`) —
это уже контракт Web service и он версионируется отдельно.

## 2. Дисциплина записи

Запись имеет **детерминированный фиксированный ABI**, а не «обязательно packed».

Правила обязательны для каждого record-типа:

1. **Фиксированный размер.** Никаких указателей, ссылок на heap-owned части,
   flexible arrays и вложенных динамических структур: запись обязана быть целиком
   перемещаемой побайтовым копированием.
2. **Никаких аллокаций.** Только массивы фиксированной длины с явными `*_MAX`.
3. **Явные лимиты.** Каждый счётчик (`*_count`) имеет максимальное значение, совпадающее
   с размером массива, который он описывает.
4. **Строки** — массивы `char[N]` с гарантированным NUL либо string table с оффсетами.
   Оффсет всегда проверяется на принадлежность таблице.
5. **Padding задаётся явно** полями `reserved[]`, а не получается случайно от компилятора.
6. **`static_assert(sizeof(record) == N)`** и **`static_assert(offsetof(поле) == K)`**
   для значимых полей.
7. **Явный порядок байт** при пересечении границы платы (LE). Внутри одной платы запись
   копируется как есть.

Естественное выравнивание допустимо, `packed` — допустим, ABI — обязателен. Причина не в
стоимости обращения к полю (на фоне записи во flash она незаметна:
`MSTORE_BENCH.md:71-78, 110-113`), а в сравниваемости байт — см. §2.1.

Запрещено:

```text
указатели и вложенные динамические структуры
TLV и другие самоописательные форматы
универсальные «мешки атрибутов»
структуры-объединения вида «все типы значения разом» (урок gw_proto_state_item_v1_t)
```

Причина запрета: фиксированный `payload_size` — основа mstore. От него зависят
`slot`-stride, размер региона и `partitions.csv` (`MSTORE.md:74-76`,
`MSTORE_FLASH_REGIONS.md:86-93`). Самоописательный формат разрушает эту опору.

### 2.1. Инвариант: все байты записи детерминированы

Canonical equality — побайтовое сравнение payload (`MSTORE.md:384-386`). Поэтому
**каждый байт записи обязан быть детерминирован**: скрытый padding и неинициализированные
поля дают ложное «изменилось», новую `version` и лишний append во flash на каждом upsert.

Отсюда обязательный приём заполнения:

```c
ha_device_record_t record = {0};        /* до заполнения полей */
```

или `memset(&record, 0, sizeof(record))`.

Это правило не стилистическое, а часть контракта: нарушение не ломает корректность, но
тихо множит запись во flash.

## 3. Изменение layout — событие, а не правка

Размер и layout записи — часть идентичности таблицы.

```text
изменился sizeof(record)  →  новая версия типа сущности
                             несовпадение с сохранённой геометрией даёт
                             INVALID_SIZE / INVALID_STATE
                             миграции нет: требуется erase раздела
                             (MSTORE_FLASH_REGIONS.md:180-185, 220-223)
```

Поэтому layout описывается один раз и не «улучшается по ходу».

## 4. Версия принадлежит хранилищу

Счётчик версии живёт в `meta` хранилища и растёт только при реальном изменении payload
(`MSTORE.md:159-192`). Поля версии **внутри** записи быть не должно: она входит в
сравниваемые байты, и тогда любая запись всегда «изменилась».

Если сервису нужен собственный счётчик ревизии, он исключается из `payload_equals`.

## 5. Ключи отдельно от записи

- ключ — **непрозрачные байты фиксированной длины**, принадлежит слою хранения;
- **не** извлекается из записи колбэком (`MICRO_DB_V1_REVIEW.md:61` — отвергнутый приём v1);
- компоненты составного ключа — **числовые и фиксированной ширины**, строк в ключах нет;
- пример, уже проверенный v1: `endpoint = (device_uid, endpoint)`,
  `group_item = (device_uid, endpoint)` (`gw_model_schema.c:42-59, 98-115`).

Формат ключа состояния уточняется вместе с Zigbee-слоем (см. §9).

## 6. Нулевой marshalling

На внутренних путях запись **не преобразуется**: Domain отдаёт её copy-out в буфер
вызывающего, сервис работает с полями напрямую (`DOMAIN_API.md §8`).

Тем самым исключаются:

- промежуточные буферы сериализации;
- второе описание тех же полей (и вечный риск их расхождения);
- аллокации в горячем пути.

Граница с браузером — исключение: там работает проекция `record → DTO`
(`WEB.md:22-33`).

## 7. Одинаковая структура ≠ доверие

Любая граница доверия (UART до Zigbee-шлюза, WS от браузера) **валидируется**, даже если
структура та же:

```text
счётчики в границах описываемых массивов
строки завершены NUL внутри своего массива
оффсеты внутри string table
идентификаторы не пустые там, где это обязательно
значения перечислений в диапазоне
связанные поля согласованы (uid ↔ short_addr, endpoint ↔ cluster)
```

Внутри доверенного кода эти проверки не дублируются (`AGENTS.md:§5.4`).

Именно поэтому в v1 при идентичных структурах существовал слой `gw_proto_trim_*` на
каждый тип (`gw_proto_validate.h:13-52`): нормализация у границы обязательна, иначе мусор
попадает в Entity Store, персистентно пишется во flash и заставляет защищаться каждого
читателя.

Domain свою границу тоже держит: размер записи сверяется с registry → `INVALID_SIZE`.
Семантическая проверка — дело сервиса-владельца.

## 8. Целостность

| Граница | Защита |
|---|---|
| UART до шлюза | CRC кадра: транспорт целостности не даёт |
| WS/TCP | транспорт уже обеспечивает целостность; второй CRC не нужен |
| Flash | CRC32 каждой записи внутри mstore (`MSTORE_FLASH_FORMAT.md:79`) |

CRC отвечает за «биты доехали», но **не** заменяет валидацию §7: кадр с корректной суммой
может нести `count = 255` при массиве на 16.

Аппаратное вычисление CRC — возможная оптимизация, но не архитектурное решение: она
допустима только по замеру и меняет только порт (`mstore/src/storage/mstore_bytes.c`).

## 9. Общий словарь Zigbee (`ha_zigbee.h`)

Формула границы: **`ha_zigbee.h` — vocabulary published by Zigbee service, not Zigbee
behavior.**

Словарь содержит только стабильные общие идентификаторы, нужные нескольким сервисам:

```text
profile_id, device_id, cluster_id, attribute_id
command_id — в той мере, в какой он нужен для идентификации
ZCL value type IDs
```

Не содержит:

```text
состояние интервью и политику повторов
допустимые переходы состояний
формирование команд и валидацию ZCL-аргументов
ESP Zigbee descriptors
```

Automation использует этот словарь для выражения триггеров и действий и при этом **не
становится зависимым от реализации Zigbee service**.

## 10. Открытые вопросы

1. **Имя и путь компонента** (принято: `esp32-p4_HA_v2/ha_model`) — уточняется в коде.
2. **Ключ состояния.** Предложение: `(device_uid, endpoint, cluster u16, attr u16)` вместо
   семантической строки v1 (`"onoff"`, `"temperature_c"`), чтобы ключ остался коротким и
   числовым; семантика остаётся проекцией Zigbee/Web (`gw_model_sync.c:236-348`).
   Решается вместе с `services/ZIGBEE.md`.
3. **`device_meta`.** Отдельный тип сущности (как в v1) или поля внутри `device`.
4. **TEXT-значение.** Компактный value журнала не имеет строк (`JOURNAL.md:49`); уточнить,
   достаточно ли этого (в v1 строковые состояния были, например weather).
5. **`payload_equals` для записи в 4 КБ** (automation): memcmp всего блока или сравнение по
   полю ревизии.

## 11. Чеклист: как добавить тип записи

```text
1. определить структуру в ha_model: без указателей, с *_MAX лимитами,
   с явно прописанным reserved[] padding
2. static_assert(sizeof == N) и static_assert(offsetof == K)
3. зафиксировать ключ: числовые компоненты фиксированной ширины
4. заполнять запись только после zero-fill (§2.1)
5. версия остаётся в хранилище; поля версии в записи нет
6. зарегистрировать тип из bootstrap:
   domain_register_entity(... sizeof(struct) ... APP_*_CAPACITY ... backing ... persist_key)
7. добавить валидацию на границах доверия (§7)
8. Web service описывает проекцию record → DTO
9. проверить пересчёт размера раздела (MSTORE_FLASH_REGIONS.md §4)
```

**Считается нарушением:** указатель или динамическая структура в записи; скрытый padding
без явного `reserved[]`; заполнение записи без zero-fill; строка в ключе; поле версии
внутри payload; TLV; отсутствие валидации на границе; дубль описания полей для транспорта
вместо проекции; «универсальный» формат ради будущего; числовой `entity_type` на проводе;
Zigbee-поведение внутри `ha_zigbee.h`; Domain, инклюдящий `ha_model`.
