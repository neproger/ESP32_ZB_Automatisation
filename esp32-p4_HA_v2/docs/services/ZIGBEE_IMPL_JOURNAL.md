# Zigbee service — журнал реализации

> Журнал ведётся по мере работы. Контракт — `services/ZIGBEE.md`.
> Здесь: текущий статус, хронология и принятые решения.

## 1. Статус

| | |
|---|---|
| Компонент | `zigbee` (IDF-компонент + host-тесты чистой логики) |
| Контракт | `services/ZIGBEE.md` |
| Реализовано | задача сервиса, репорт → состояние, топология endpoint'ов, интервью устройства (ZDO-дискавери + Basic), подписка на состояние (binding + Configure Reporting), события от устройств (сырой ZCL-кадр → EVENT), executor и отправка команд, комиссионирование (formation/open/steering), радиоканал ESP-Hosted + RCP, счётчики диагностики |
| Заглушки | нет |
| Тесты | host: `test_state`, `test_command`, `test_topology`, `test_interview` (чистая логика без FreeRTOS) |
| Проверено на P4 | живое устройство (ESP32C6-DISPLAY): сеть, интервью, device + endpoint'ы в Domain |

Сервис разделён по признаку «что можно проверить на хосте»:

```text
zigbee_state.c      репорт → ключ, запись; модель устройства       host + IDF
zigbee_command.c    проверка команды до отправки                    host + IDF
zigbee_topology.c   запись endpoint'а                               host + IDF
zigbee_interview.c  роли кластеров и запись интервью в Domain       host + IDF
zigbee.c            задача, очереди, executor                       только IDF
zigbee_radio.c      ESP-Hosted + RCP, репорт, команды и интервью    только IDF
zigbee_binding.c    подписка: client-кластеры, bind, reporting      только IDF
zigbee_diag.c       счётчики и печать ошибок                        только IDF
```

## 2. Хронология

```text
1. контракт сервиса                     services/ZIGBEE.md (роль, потоки, контексты)
2. ключ состояния и гранулярность       решено: числовой ZCL-ключ, запись на атрибут
3. формы сущностей в ha_model           ha_entities.h: device / state / endpoint
4. приложение от корня                  ha_p4: bootstrap, диспетчер, журнал в консоль
5. приём репорта                        zigbee_state.c + задача сервиса
6. выделение чистой логики              host-тесты маппинга и геометрии
7. команды                              executor + проверка адресата + очередь отправки
8. адресат факта                        domain_fact_target_t в Domain
9. топология                            endpoint и состав кластеров
10. счётчики диагностики                zigbee_diag, отдельно от Journal
11. радиоканал                          zigbee_radio: ESP-Hosted -> RCP -> стек, репорты
12. отправка команд                     zigbee_radio_send: On/Off, Level MoveToLevel
13. комиссионирование                   formation/open(180с)/steering, лог permit-join
14. интервью устройства                 Active_EP -> Simple_Desc -> Basic, upsert в Domain
15. подписка на состояние               client-кластеры координатора, bind + reporting
16. события от устройств                raw ZCL-кадр -> domain_payload_put (EVENT)
```

## 3. Принятые решения

| Дата | Решение | Почему |
|---|---|---|
| 2026-10-01 | Ключ состояния — числовой `(uid, endpoint, cluster, attr)` | та же координата, что в ZCL-репорте; не появляется вторая система идентификаторов |
| 2026-10-01 | Runtime state — одна сущность на атрибут | точный смысл `changed`; mstore рассчитан на маленькие записи с append только при изменении |
| 2026-10-01 | Устройство — `RAM\|FLASH`, состояние и топология — RAM | имя и модель должны переживать перезагрузку; состояние приносят репорты, топологию — интервью |
| 2026-10-01 | Чистая логика сервиса без FreeRTOS и логирования | иначе её нельзя прогнать на хосте |
| 2026-10-01 | Адресат факта — отдельный параметр `domain_fact_target_t`, а не поле `meta` | у операций над сущностями адресат известен из операции; два источника одной истины дали бы скрытый приоритет |
| 2026-10-01 | Адресат проверяется до executor'а | при неизвестном типе `COMMAND_SENT` не пишется вовсе |
| 2026-10-01 | Номер endpoint'а только в ключе, не в записи | одна истина; запись не дублирует ключ |
| 2026-10-01 | Диагностика — счётчики сервиса + консоль, а не Journal | пачка однотипных ERROR вытесняет из ring факты состояния |
| 2026-10-01 | Сбой считает тот, кто его обнаружил | при двойной записи один отказ давал два счётчика |
| 2026-10-01 | Радио — UART-RCP через ESP-Hosted, а не нативный 802.15.4 | у P4 нет радио; C6 отдаёт его как RCP, host-стек Zigbee тот же |
| 2026-10-01 | Команда адресуется EUI-64, short address разрешает стек | identity устройства не зависит от текущего сетевого адреса |
| 2026-10-01 | Отправка из задачи сервиса, а не радио | радио-задача занята mainloop'ом; ezb_* cmd_req сериализуются стеком |
| 2026-10-03 | Устройство без интервью — только RAM сервиса, в Domain — по завершении интервью | топология и модель приходят заново на каждом rejoin; частичное устройство в Domain не появляется |
| 2026-10-03 | Интервью завершается по счётчику ответов; Basic читается с endpoint'а, где он есть | у устройства есть служебные endpoint'ы без Basic — чтение «с первого» ответа не даёт и подвешивает интервью |
| 2026-10-03 | Запись интервью в Domain — в задаче сервиса, а не в колбэке радио | Domain пишет один потребитель (задача сервиса); радио только собирает и кладёт в очередь |
| 2026-10-03 | После интервью координатор сам подписывается на state-кластеры устройства | устройство не шлёт состояние без binding'а и Configure Reporting |
| 2026-10-03 | Таблица reportable-атрибутов одна: из неё и client-кластеры, и reporting | иначе список кластеров-приёмников и список подписки разошлись бы |
| 2026-10-03 | События — через сырой ZCL-кадр, а не отдельный колбэк | privilege-команды в SDK отключены, а для OnOff On/Off/Toggle нет колбэка |

## 4. От чего отказались

```text
кэш состояния внутри сервиса          — истина только в Domain
персистентность состояния и топологии — данные приходят заново, платить за flash нечем
фильтр по ключу в Dispatcher'е        — подписчик сравнивает ключ сам; потребителя ещё нет
троттлинг печати ошибок               — механизма без измеренной потребности не вводим
```

## 5. Прошивка C6 (RCP)

Характеристики платы, распиновка JP1 и полная процедура прошивки C6 (включая сборку
CP-прошивки с RCP) — в справочнике `../hardware/JC4880P443C_I_W.md` §6.

Статус: прошито и проверено. CP-прошивка включает Wi-Fi и RCP (OpenThread), спинel
RCP вынесен на `GPIO17/16` (иначе UART занимает `D0/D1` SDIO и стек падает). C6 шьётся
внешним 3.3 В USB-TTL в JP1. Детали — `../hardware/JC4880P443C_I_W.md` §6.
