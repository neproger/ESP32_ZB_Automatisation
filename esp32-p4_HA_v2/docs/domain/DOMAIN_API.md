# Domain API

> **Статус:** черновой контракт фасада. Карта системы — `../ARCHITECTURE.md`.
> Документ отвечает на вопрос **«как сервис разговаривает с Domain»**. Внутреннее
> устройство подсистем описывают их собственные документы (`ENTITY_STORE.md`,
> `JOURNAL.md`, `DISPATCHER.md`, `COMMANDS.md`, `TRANSIENT_PAYLOAD.md`).
> Точные сигнатуры, типы и размеры уточняются в коде.

## 1. Роль и граница

Domain — **инфраструктурное ядро фактов**, а не носитель бизнес-логики. Он отвечает
на вопросы «где хранить, как передать, кого разбудить и когда». Семантика принадлежит
сервисам.

```text
сервис знает:              Domain знает:
  что такое endpoint         как найти запись по key
  что значит cluster 0x0006  где физически лежит payload
  когда правило истинно      кого и в каком порядке уведомить
```

Сервисы живут данными из Domain, но Domain не понимает, почему эти данные кому-то
интересны. Он даёт единый факт, единый порядок записи и единую доставку изменения.

**Domain не знает про:** смысл конкретных сущностей и атрибутов, допустимые переходы
состояний, процедуры создания и удаления устройств, роли и permissions, UI/pending,
lifecycle и корреляцию команд, форматы внешних протоколов (`ARCHITECTURE.md:172-173`).

## 2. Namespace и нейминг

Публичная поверхность Domain — только `domain_*`. Сервис не вызывает ничего ниже
фасада, включая Entity Store напрямую.

```text
domain_*            публичный API для сервисов
<субсистема>_*      внутренние механизмы Domain
mstore_*            слой хранения, сервисам не виден (см. §5)
```

Имя операции описывает действие над **сущностью** или **механизмом**, а не «обработку»:
`domain_entity_put`, `domain_post`, `domain_payload_get`. Общих имён (`handle`,
`process`, `update`) нет.

## 3. Ошибки

Модель ошибок единая для всего фасада — `domain_err_t`. Внутренние коды подсистем и
`mstore_err_t` наружу не выходят: сервис не должен уметь отличать «слот протух» от
«раздел заполнен».

| Код | Смысл для вызывающего |
|---|---|
| `OK` | операция выполнена |
| `NOT_FOUND` | сущность/ключ/подписчик не существует |
| `NO_SPACE` | место закончилось; запись не принята |
| `INVALID_ARG` | аргумент не задан или вне диапазона |
| `INVALID_SIZE` | размер записи/ключа не совпадает с типом сущности |
| `INVALID_STATE` | Domain не инициализирован или уже инициализирован |
| `NO_MEM` | нет памяти под внутренние структуры |
| `STALE` | протухшая ссылка: transient-payload вытеснен либо физический слот переиспользован |
| `BUSY` | ресурс занят, повтор уместен |
| `IO` | отказ физического носителя |
| `CORRUPT` | нарушена целостность хранимого состояния |
| `OVERFLOW` | исчерпан внутренний счётчик записи |

Правила:

- ошибка возвращается, а не «побеждается» молча: пустой результат и «не удалось
  получить результат» — разные исходы;
- `CORRUPT` и `IO` не лечатся внутри Domain: тихого переформатирования и fallback нет
  (`MSTORE_FLASH_REGIONS.md:196-202`);
- диагностичность — в реализации; контракт фиксирует только устойчивый код.

## 4. Identity и opaque-типы

Domain владеет доменными identity. Их внутреннее устройство сервису неизвестно:

```text
domain_entity_t        — дискриминатор типа сущности (ключ registry)
domain_event_id_t      — identity записи Journal
domain_payload_ref_t   — ссылка на transient payload
```

Степень прозрачности разная — это важно:

| Тип | Для сервиса |
|---|---|
| `domain_event_id_t`, `domain_payload_ref_t` | **полностью opaque**: только копирование и сравнение |
| ключ сущности | opaque для Domain, **typed для сервиса** через `ha_model` |

Ключ сущности — непрозрачная последовательность байт фиксированной длины; длина задаётся
типом сущности. Но сервис **строит** его сам по типизированному layout:

```c
ha_endpoint_key_t key = { .device_uid = uid, .endpoint = ep };
```

Domain видит те же байты как opaque: состав ключа для него не существует
(`RECORD_MODEL.md` §5).

`event_id` и `payload_ref` сервис не разбирает никогда: никакой арифметики и никаких
предположений о внутреннем формате.

## 5. Правило: `mstore_*` наружу не выходят

Типы и понятия хранения (`slot`, `generation`, `version`, `seq`, ring-функции) —
внутренность Domain. Сервис работает с ключами, записями и доменными identity
(`ARCHITECTURE.md:169-171`, `MSTORE.md:592-596`).

Реализация вправе кодировать `event_id` через seq напрямую — таблица соответствий не
нужна; для сервиса это opaque.

## 6. Lifecycle

```text
domain_init()
    поднять таблицы Entity Store
    поднять Journal и transient payload ring
    зарегистрировать executors команд
    запустить Dispatcher
```

- до `domain_init()` любой вызов — `INVALID_STATE`;
- регистрация сущностей и команд — часть инициализации, не runtime-механизм: новый
  тип/команда появляется только вместе с кодом, который их использует
  (`ARCHITECTURE.md:202`);
- Domain не содержит таблицы известных типов и не включает компонент форм данных
  (`RECORD_MODEL.md` §1.1): descriptors приходят из bootstrap через
  `domain_register_entity()`;
- сервисные задачи стартуют после `domain_init()`;
- `domain_deinit()` существует для host-тестов и переинициализации.

## 7. Registry и поиск сущностей

Типы сущностей **равны**: Domain не выделяет «главные» и «подчинённые». Registry —
простая таблица маршрутизации, собранная из descriptors, переданных при регистрации:

```text
domain_entity_t → { таблица/схема, optional validate }
```

descriptor задаёт `type`, `key_size`, `payload_size`, `capacity`, `backing`,
`persist_key`. Размеры и политику хранения определяет bootstrap приложения, а не Domain:
см. `RECORD_MODEL.md` §1.1.

- type нужен только чтобы выбрать хранилище; hooks и schema-колбэки для Journal нет
  (`ENTITY_STORE.md:16-25`);
- поиск по ключу даёт запись целиком; запись — блок байт фиксированного размера,
  заданного типом; Domain содержимое не интерпретирует;
- списки и связи — данные, а не отношения Domain: `list(entity, prefix)`, составные
  ключи, ссылки внутри записи. Relationship-таблиц нет (`ENTITY_STORE.md:54-61`);
- фильтры богаче prefix-range добавляются только под доказанного потребителя.

## 8. Ownership, copy-out, время жизни колбэка

Правила единые для всего фасада:

- **copy-in:** Domain копирует данные вызывающего при записи; после возврата из вызова
  сервис волен Dispose свой буфер;
- **copy-out:** чтение отдаёт данные в буфер вызывающего, размер которого задан типом
  сущности; несовпадение размера — `INVALID_SIZE`;
- **никаких borrowed pointers** после возврата из вызова: Domain не отдаёт сервису
  указатель в свою память;
- **колбэк:** указатели, переданные в колбэк (итерация, доставка), действительны только
  на время вызова и не должны сохраняться;
- transient payload — исключение по смыслу, но не по владению: это best-effort-окно
  внутри Domain, ref выдаётся наружу как opaque (`TRANSIENT_PAYLOAD.md:14-27`).

## 9. Threading, lock, реентрантность

- фасад можно вызывать из любой сервисной задачи; синхронизация — внутренность Domain;
- один lock на экземпляр Domain: под ним целиком идут mutation path (`put` / `remove`),
  read path (`get` — пишет ключ в scratch типа) и `iter`. Lock **не рекурсивный**;
- сериализация mutation path — не оптимизация, а контракт: без неё последовательность
  `slot_find → slot_meta → slot_update` рвётся и `put` возвращает `STALE`. С сериализацией
  `STALE` для операций над сущностями недостижим и остаётся только семантикой payload;
- **порядок записи сериализован:** запись состояния и запись факта в Journal идут в одном
  порядке (`ENTITY_STORE.md:70-76`);
- producer не вызывает подписчиков: он пишет состояние и факт и возвращается; доставка —
  задача Dispatcher'а (`DISPATCHER.md:8-14`);
- **колбэк итерации не вызывает мутирующий API Domain** — рекурсивность внутреннего
  lock'а не является частью контракта;
- executor команды вызывается **синхронно в контексте вызывающего**: `domain_post()`
  возвращается, когда команда передана (`COMMANDS.md:26`). Executor обязан быть коротким
  и не ждать подтверждения от устройства;
- логика подписчика выполняется в его собственной задаче, а не в контексте producer'а и
  не в контексте Dispatcher'а.

## 10. Точки входа подсистем

Только перечень границ — поведение описывают документы подсистем.

| Подсистема | Что даёт сервису | Поведение |
|---|---|---|
| Entities | `domain_register_entity` (bootstrap) / `put / get / remove / iter`; `put`/`remove` пишут факт при реальном изменении | `ENTITY_STORE.md` |
| Journal | прямой доступ отсутствует: Journal читает только Dispatcher | `JOURNAL.md` |
| Subscriptions | подписка (`contact + filter`), ожидание события | `DISPATCHER.md` |
| Commands | `domain_post` + регистрация executor'а | `COMMANDS.md` |
| Transient payload | `domain_payload_put / get` по opaque ref | `TRANSIENT_PAYLOAD.md` |

Команда и событие — разные вещи: команда идёт напрямую исполнителю и лишь журналируется
как `COMMAND_SENT`; событие идет подписчикам через Dispatcher (`COMMANDS.md:10-14`).

## 12. Открытые вопросы

1. **Нейминг.** Фасад — `put / get / remove / iter`, а `ENTITY_STORE.md:29-34` описывает
   операции как `get / list / upsert / remove`. Привести документ подсистемы к именам
   фасада.
2. ~~**Put без изменения.**~~ Решено: повторение не считается изменением — запись
   `ENTITY_UPSERTED` не создаётся, подписчики не будятся, вызывающий получает
   `changed = false` (`ENTITY_STORE.md` §8). Факт «что-то произошло» при неизменном
   состоянии — это `EVENT`, а не upsert.
3. **Meta-запрос.** Нужен ли сервису дешёвый opaque-version сущности без чтения записи
   (polling Display) или достаточно `get`.
4. **Чтение Journal сервисом.** История для UI — только через подписку или нужен
   отдельный read-путь.
5. **`BUSY`.** Есть ли сценарий, где Domain вынужден отказать в приёме, а не вытеснить
   старое (политика ring утверждает обратное: `JOURNAL.md:56-63`).
6. Фильтрация подписок и владение inbox — открыты в `DISPATCHER.md:51-55`; здесь не
   дублируются.
